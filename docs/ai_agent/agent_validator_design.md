## 1. 전체 흐름

```
LLM 호출 ─→ ① 파싱 ─→ ② 자동 복구 ─→ ③ 검증(규칙 전체)
                                         │
                      ┌──────────────────┴──────────────────┐
                    통과                                   실패
                      │                                     │
               message_source="llm"                 재시도 여유가 있나?(남은 시간 ≥ 4초)
                                                  ┌─────┴─────┐
                                                 예           아니오
                                         실패 사유를 덧붙여      │
                                         1회 재호출 → 재검증     │
                                          ┌───┴───┐            │
                                        통과     실패          │
                                          │       │            │
                                    retry_pass    └─────┬──────┘
                                                        ↓
                                            ④ 항목 단위 폴백 판정
                                      ┌─────────────┴─────────────┐
                              문구·근거만 실패한 항목만             구조 실패(JSON·스키마·후보 밖·개수 등)
                              템플릿으로 교체(부분 폴백)            전체를 템플릿으로(전체 폴백)
```

| 결과(`outcome`) | 의미 | 화면 표시 `[제안]` |
|---|---|---|
| `pass` | 1차 통과 | "AI 작성" |
| `retry_pass` | 재시도 후 통과 | "AI 작성" + 검증 패널에 재시도 1회 |
| `partial_template` | 일부 항목만 템플릿 | 항목별 "AI 작성" / "기본 문구" |
| `full_template` | 전체 템플릿(LLM 오류·타임아웃·키 없음 포함) | 전 항목 "기본 문구" |
| `survey_template` | `SURVEY_ONLY`: LLM 없이 만족도 조사 템플릿 | "기본 문구" |
| `no_action` | 후보 0건(대체 꺼짐), `NONE`, `SURVEY_ONLY`인데 만족도 조사가 쿨다운 | "제안할 조치 없음" |

**모의 LLM 표시**: `llm.provider: mock`이면 규칙 기반 mock이 템플릿과 같은 문구를 만들어 검증을 통과하므로 `outcome=pass`, `message_source=llm`으로 기록됩니다. 화면은 응답의 `meta.llm_provider`(`mock`)를 보고 "모의 LLM"으로 표시해야 합니다 `[제안]`. (`action_log.message_source`는 `llm`/`template`만 허용하므로 값은 그대로 두고 표시만 구분.)

화면에는 결과 카드 아래에 접힌 "검증 결과" 패널을 두고 재시도 횟수, 실패한 규칙, 문구 출처를 보여 줍니다. 시연에서 **LLM을 믿는 구조가 아니라 확인하는 구조**임을 보여 주는 장면이 됩니다 `[제안]`.

## 2. 단계별 처리

### 2.1 ① 파싱과 ② 자동 복구 `[구현]`

| 문제 | 처리 |
|---|---|
| ```` ```json ```` 코드 블록으로 감쌈 | 벗겨냄(`R5_FENCE_STRIPPED` 기록) |
| JSON 앞뒤에 설명 문장 | 첫 `{`부터 마지막 `}`까지 추출(`R5_TEXT_STRIPPED` 기록) |
| 스키마에 없는 필드 | OpenAI strict 스키마가 막고, API 응답 모델에서도 빠짐. 비용·구분·채널은 어차피 카탈로그에서 채움 |
| `priority` 순서가 뒤섞임 | 검증기가 1..n 연속인지만 보고, 결과를 우선순위 순으로 정렬(서비스) |

복구하지 **않는** 것: 후보 밖 ID, 숫자·문구 내용, 누락된 필수 필드. 의미를 코드가 짐작해 고치면 안 되기 때문입니다.

### 2.2 ③ 검증 규칙 전체 (v3)

**hard**는 실패 시 재시도·폴백 대상, **soft**는 기록만 하고 통과(품질 지표). "고객 글"은 고객에게 가는 제목과 본문이며, 검사 전에 NFKC 정규화와 보이지 않는 문자 제거를 합니다.

| 형식 | `R5` | JSON 파싱 실패 | hard |

## 3. 숫자 대조 방식 (R2, M3, E3)

LLM이 가장 쉽게 어기는 부분이라 규칙을 구체적으로 정합니다. 핵심은 **글마다 허용하는 숫자 집합이 다르고, 고객 글은 단위까지 맞춘다**는 것입니다.

### 3.1 허용 집합

| 글 | 허용하는 숫자 | 비교 |
|---|---|---|
| 고객 글(제목·본문) | 구독 속성: 월 요금(원), 약정 기간(개월, 12의 배수면 년), 종료까지 일수(일), 종료일·케어 연장일·프로모션 종료일의 년·월·일. `message_facts`: 종류별 단위(원, 개월, 회, 일, 날짜). **해당 후보**의 이름·상세·문구 힌트·고객용 제목·버튼 안의 숫자(단위 없이 나오면 단위 무관) | (값, 단위). 숫자 뒤에 단위가 없으면 값만 비교. "두 가지"처럼 4 이하의 '가지'는 허용 |
| 선택 이유 | 고객 글 허용값(단위 무시) + 해당 항목 evidence 값(0~1 비율은 % 환산 포함) + evidence 피처 라벨 안의 숫자("최근 90일"의 90) + 해당 유형의 기여 비중(%)·순위 + 설정 숫자(만족도 조사 추천 순위 20·30) + 1 | 값 |
| 내부 전달서 | 위 값 + 내부 분석값(유형·SHAP·`context`·`facts`·확률·순위·후보 수) | 값 |
| 요약 | 선택 항목들의 선택 이유 허용값 + 1..후보 수 | 값 |

고객 글에 허용 집합 밖의 숫자가 나왔을 때, 그 숫자가 **내부 분석값에 있으면 `M3`, 아예 입력에 없으면 `R2`**로 구분합니다. 재시도 메시지가 "내부 수치를 쓰지 말라"와 "입력에 없는 숫자를 쓰지 말라"를 구분해 알려 줍니다.

단위를 맞추는 이유: 값만 보면 "약정 종료까지 192일"의 192를 "192원"으로 써도 통과합니다. 단위를 함께 보면 이런 오용이 `R2`로 걸립니다.

초기 프로토타입에서 선택 이유의 허용 집합을 입력 전체 숫자로 넓게 잡았더니 **"위약금 문의 7회"가 통과**했습니다(실제 값은 4회, 문의 총건수가 7). 그래서 선택 이유는 evidence 값과 일치하는 숫자만 허용하도록 좁혔습니다.

### 3.2 숫자 추출 규칙

| 표기 | 처리 |
|---|---|
| `68,000원` | 68000(원) |
| `6만 8천 원`, `6.8만 원` | 68000(원) |
| `삼만 원`, `오천 원`, `만 원` | 30000, 5000, 10000(원) |
| `두 번`, `세 건`, `열 달` | 2, 3, 10 ("한 번"은 관용 표현이 많아 제외) |
| `2026년 10월 21일`, `2026.10.21`, `2026-10-21` | (2026, 년), (10, 월), (21, 일) |
| `10/21` | (10, 월), (21, 일) |
| `1:1 상담` | 숫자로 보지 않음 |
| `53%`, `53퍼센트` | 53(%) |
| 유형 ID(`T02`), 솔루션 ID(`S-T02-A`) | 숫자 추출 전에 제거. 고객 글에 나타나면 `LEAK` |
| 범위 `2~4` | 각각 추출 |

### 3.3 한계 `[가정]`

- **숫자와 의미의 짝**은 확인하지 못합니다. 단위가 같은 다른 값(예: 남은 케어 1회 자리에 다른 "1회")은 통과합니다. 선택 이유에서는 evidence와 짝을 맞추도록 프롬프트(E3)로 유도하고, 사람 평가에서 확인합니다.
- 계산 결과("월 요금 × 12개월")는 입력에 없는 숫자라 `R2`로 걸립니다. 의도한 동작입니다.
- 목록에 없는 한글 수사(열두 개 등)는 일부 못 잡습니다. 실제 모델 출력에서 나오는 표기를 보고 보완합니다.

## 4. 재시도 메시지 `[구현]`

재시도는 **1회**(`[확정]`)이며, 이전 출력 전체를 다시 보내지 않고 같은 사용자 메시지 뒤에 **실패한 규칙과 위치만** 붙입니다.

```
[재작성 요청] 이전 출력이 아래 규칙을 어겼습니다. 해당 부분만 고쳐 같은 JSON 형식으로 다시 출력하세요.
- M7 (항목 1): 고객 문구: 금지 표현(놓치면)
- M7 (항목 1): 고객 문구: 금지 표현(손해)
- R2 (항목 1): 고객 문구의 숫자 32000(won): 입력·고객 공개 값에 없음
```

- 메시지는 검증기가 만든 문장입니다. LLM이 쓴 문장이나 고객 데이터를 통째로 인용하지 않고, 걸린 표현 패턴·숫자·식별자 수준만 알려 줍니다(같은 표현 반복과 주입 경로를 줄이기 위함).
- hard 실패만 알려 주고, soft(경고)는 알려 주지 않습니다.
- 재시도 temperature 조정은 구현하지 않았습니다(기본으로 temperature를 보내지 않음). 필요하면 실제 모델 평가 후 추가 `[제안]`.
- 재시도에서도 실패하면 재재시도 없이 항목 단위 폴백으로 갑니다.

## 5. 폴백

### 5.1 템플릿 `[구현]`

문구는 `agent_prompt_design.md` §8(보고서 형식: `customer_title` 첫 문장 + `message_facts` ▶ 줄 + 구분별 마무리)을 씁니다. 템플릿은 **검증기를 통과하는 것이 보장돼야** 하므로, 에이전트가 고를 수 있는 솔루션 36개 전부를 `message_facts`가 있을 때와 없을 때 각각 검증기에 넣는 시험을 둡니다(`tests/test_fallback_v3.py`).

| 필드 | 폴백 값 |
|---|---|
| `title` | `customer_title`(광고성이면 `(광고) ` 접두, 40자) |
| `message_text` | 보고서 형식 템플릿. 순수 내부 전달이면 빈 문자열 |
| `internal_memo` | 내부 전달 솔루션이면 "[내부 전달] {솔루션} 건입니다. 전달 부서: {부서}. 구독자 정보를 확인해 조치해 주세요." |
| `selection_reason` | "규칙 엔진이 선택한 후보를 우선순위 순서대로 제안합니다." |
| `evidence` | **코드가 만듦**: 해당 유형 `top_features` 상위 2개. NO_TYPE이면 `risk_level`, `risk_rank_pct`. 둘 다 없으면 월 요금 |
| `summary` | "규칙에 따라 후보 조치를 순서대로 제안합니다." |
| 순서·구분·이름·비용 | Rule Engine 후보 순서 그대로, 카탈로그 값 |

폴백에서도 `evidence`를 의미 있게 채워, 전체 폴백이 되어도 화면에서 "왜 이 조치인지"를 숫자로 볼 수 있게 합니다.

### 5.2 부분 폴백과 전체 폴백

| 실패 종류 | 처리 | 이유 |
|---|---|---|
| 특정 항목의 문구·근거·숫자·제목·전달서 위반(`M*`, `E*`, `N*`, `T*`, `D*`, `R2`, `R1_TYPE`, `LEAK`, `LANG`) | **그 항목만** 템플릿으로 교체, 나머지 LLM 항목 유지 | 이미 통과한 항목까지 버리면 낭비 |
| 구조 문제(`R5`, `SCHEMA`, `R1`, `R1_COUNT`, `R1_EMPTY`, `R1_DUP`, `R1_CAT`) | 전체를 템플릿으로 | 어떤 항목이 믿을 만한지 판단할 근거가 약함 |
| `summary`만 위반 | summary만 고정 문장으로 교체 | |
| 검증기 자체 오류(예외) | `SCHEMA`로 기록하고 전체 템플릿 | 검증되지 않은 문구가 나가지 않게 |

**빈 선택(`selected=[]`)은 허용하지 않습니다** `[확정]`. 후보는 Rule Engine이 이미 안전하다고 판정한 목록이라 LLM이 거부권을 가질 이유가 없고, 빈 선택을 허용하면 조용히 제안이 사라지는 경로가 생깁니다(`agent_design.md` §3.4).

### 5.3 시간·오류 처리 `[구현]`

| 상황 | 처리 | 기록 |
|---|---|---|
| 타임아웃(1차 10초, 재시도 8초) | **재시도하지 않고** 템플릿. 같은 이유로 또 지연될 가능성이 높고 사용자가 기다림 | `TIMEOUT` |
| 429, 5xx, 상태 코드 없는 오류(빈 응답, 모델 거부, 출력 길이 초과, 콘텐츠 필터 포함) | 남은 시간이 4초 이상이면 1회 재호출(검증 재시도와 같은 1회로 계산) | `LLM_ERROR` |
| 400, 401, 403, 404 | 다시 보내도 같으므로 재시도 없이 템플릿 | `LLM_ERROR` |
| 키 없음 | 처음부터 템플릿 | `LLM_UNAVAILABLE` |
| 전체 마감 | 요청당 15초. 남은 시간이 4초 미만이면 재시도 건너뜀 | |

- OpenAI SDK의 자동 재시도는 끄고(`max_retries=0`) 재시도·시간 한도는 폴백 모듈이 통제합니다.
- 오류 요약(최대 200자)은 응답의 `meta.llm_errors`와 `agent_result.result_json`에 남습니다. 저장 전에 키 조각(`sk-…`, `Bearer …`)을 `[가림]`으로 바꿉니다(OpenAI 401 메시지에는 일부 가려진 키가 섞여 옴).
- 타임아웃 값은 실제 모델의 응답 시간(p50, p95)을 보고 다시 정합니다 `[가정]`.

### 5.4 LLM 없이 동작하는 경로

| 설정 | 동작 |
|---|---|
| `llm.provider: mock` (기본) | 규칙 기반 mock이 후보 순서대로 템플릿 문구를 JSON으로 냄. 검증을 거쳐 `pass`. `meta.llm_provider='mock'`, `/health`의 `llm_status='mock'` |
| `llm.provider: openai` + 키 없음 | 앱은 기동하고 모든 요청이 `full_template`(`LLM_UNAVAILABLE`). `/health`의 `llm_status`가 `unavailable: …` |
| `llm.provider: openai` + 키 있음 | 실제 호출. `/health`의 `llm_status='ready'` |

개발 중과 시연 중 장애에도 Agent가 끝까지 돌아가게 하는 안전 경로입니다.

## 6. 응답 시간·토큰·비용 `[가정]`

모델명이 정해지지 않아 실측 전입니다. 아래는 글자 수로 본 규모이며, 토큰 수는 토크나이저로 재지 못해 추정입니다.

| 항목 | 규모 | 근거 |
|---|---|---|
| 입력 | 시스템 프롬프트 3,825자 + 사용자 입력 약 2,500자(후보 2개, 데모 D2) + 응답 스키마 약 900자 → **약 7,200자** | 코드에서 잼 |
| 출력 | 항목 2개 기준 약 950자 | `agent_prompt_design.md` §7 예시 |
| 토큰 | 입력 약 4,000~7,000, 출력 약 600~1,000 | 한국어 글자당 0.6~1토큰 `[가정]` |
| 재시도 시 추가 | 입력 + 재작성 요청(수백 자) | 이전 출력은 다시 보내지 않음 |
| 호출 빈도 | 상담자가 구독자를 선택해 실행할 때만 1건 | 전 구독자 대상 일괄 호출 없음 |

시스템 프롬프트는 모든 호출에서 같으므로 API의 프롬프트 캐싱이 적용되면 입력 비용이 줄어듭니다(모델 선정 때 확인).

**기록**: 호출 로그 테이블(`agent_llm_log`)은 만들지 않습니다 `[확정 2026-10-07]`. `agent_result`에 `outcome`, `attempts`, `failed_checks`, `llm_provider`, `llm_model`, `prompt_version`, 결과 전체(`result_json`)를 저장합니다. 토큰 수·지연 시간은 아직 저장하지 않으며, 비용 실측이 필요해지면 `agent_result`에 `input_tokens`, `output_tokens`, `latency_ms`를 추가합니다 `[제안]`. 결과 캐시(같은 입력이면 검증 통과 결과 재사용)는 구현하지 않았습니다 `[제안]`.

### 6.1 평가 하네스 `[제안]` (미구현)

모델명이 정해지면 시연·샘플 데이터의 ACTION·NO_TYPE 케이스 N건을 실제로 돌려 한 표로 냅니다.

| 지표 | 목표 (프롬프트 설계 §10.2와 동일) |
|---|---|
| JSON 형식 유효율 | 99% 이상 |
| 후보 밖 선택 | 0건 |
| 숫자 대조 통과율 | 98% 이상 |
| 금지 표현 | 0건 |
| 길이·형식 규칙 준수 | 95% 이상 |
| 템플릿 폴백 비율 | 5% 이하 |
| 1차 통과율 / 재시도 후 통과율 | 기록 |
| 호출당 토큰, 지연 시간 p50·p95, 호출당 비용 | 기록(모델 선정 근거) |
| 규칙별 실패 빈도 | 상위 규칙을 프롬프트 수정 대상으로 |

이 표가 "모델이 정확하게 결과물을 뽑아내는지와 토큰 비용"을 보자는 팀 결정(2026-10-06)의 측정 방법입니다. 모델 후보가 둘 이상이면 같은 케이스로 비교합니다.

## 8. 설정값

`config.yaml`의 `llm` 항목(현재 값):

```yaml
llm:
  provider: mock                 # mock | openai
  model: gpt-4o-mini             # [팀 결정 필요] 자리표시자
  api_key_env: OPENAI_API_KEY    # 키는 환경변수로만
  temperature: null              # null이면 보내지 않음
  first_timeout_s: 10
  retry_timeout_s: 8
  deadline_s: 15
  max_message_chars: 400         # 본문 한도
  banned_phrases_extra: []       # 팀이 추가할 금지 표현(M7)
```

코드에 고정된 값(`agent/validation/validator.py`): 제목 40자, ▶ 4줄·한 줄 60자, 선택 이유 100자(140자 초과면 hard), 요약 150자, 내부 전달서 300자, 재시도 최소 여유 4초(`fallback.py`), 표현 목록(`PRESSURE`, `INTERNAL_WORDS`, `BENEFIT_GROUPS`, `CONFIRM_PAY`, `PROMISE`)과 구분별 필수 키워드. 팀 검토에서 자주 고칠 값이 생기면 설정으로 옮깁니다 `[제안]`.

### 9.2 초기 프로토타입 (2026-10-06, 기록)

`validator_prototype/`로 위반 사례 25개·정상 사례 5개, 폴백 시나리오 7개, 템플릿 8종을 확인했습니다. 이때 걸린 문제 두 가지(선택 이유 숫자가 입력 전체와만 대조돼 틀린 값이 통과, 한글 금액 미인식)는 §3에 반영했습니다. 현재 코드는 이 프로토타입을 대체합니다.

**한계**: 규칙이 작동하는지 본 것이고, **실제 LLM 출력 분포에서 오탐(정상인데 걸림)·미탐(위반인데 통과)이 얼마나 나는지는 모릅니다.** 특히 M8·M4는 "필요한 단어가 있는가"를 보는 키워드 검사라 표현이 다른 정상 문구가 걸릴 수 있습니다. 실제 모델 평가(§6.1)로 키워드를 늘리거나 soft로 낮출지 정합니다.
