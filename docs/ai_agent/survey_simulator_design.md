## 0. 문서 성격과 표기

- 실제로 설문을 돌리지 않으므로, **고객 한 명이 이 설문에 어떻게 답할지를 규칙으로 정해 응답을 만드는 방법**을 정의합니다. 응답은 모두 가설 기반 synthetic data이며, 실제 고객 응답이 아닙니다.
- 응답을 우리 유형·피처에서 만들어 내므로 **신규 유형 "발견"의 근거가 아니라 파이프라인 작동 확인용**입니다. 발표 자료에도 그렇게 표기합니다.
- 표기: `[확정]` 합의된 내용 / `[팀 결정 필요]` / `[제안]` / `[가정]` 근거 없이 둔 시작값.
- **이탈 유형은 10개로 확정**(2026-10-07)됐고 **솔루션 38건도 확정**(2026-10-07, `solution_catalog_design.md`)됐습니다. 유형·솔루션에 의존하는 규칙은 §2의 매핑표(`survey_mapping.yaml`)로만 모으고, 나머지 규칙은 설문 보기 코드와 관측 데이터(피처)에만 의존하게 만들었습니다. §2.5는 확정 솔루션 ID로 갱신했고, §2.3~§2.4의 솔루션 연동은 아직 점검 전입니다 `[제안]`.
- 유형 ID는 `churn_types_10.md`의 안(T01~T10)을 씁니다(ID 체계는 `[제안]` 상태).

## 1. 기본 원칙 `[제안]`

1. **관측 데이터가 있으면 거기서 답을 정합니다.** 방문이 몇 번 미뤄졌는지, 같은 증상이 몇 번 반복됐는지는 이미 이벤트 테이블에 있습니다. 설문이 데이터와 모순되면 시연에서 바로 들통납니다.
2. **관측 데이터로 정해지지 않는 문항은 잠재 유형 활성 강도로 확률 샘플링합니다.** (`synth_truth_type.activation_strength`, 0~1)
3. **일부러 노이즈를 넣습니다.** 모든 응답이 유형과 일치하면 후보 생성 검증이 의미가 없습니다. 기존 문서의 비율을 따릅니다: 자기 유형과 맞는 사유 60%, 다른 기존 유형 10%, 숨은 신규 주제 20%, 기타 10% `[가정]`.
4. **숨은 신규 주제는 관측되지 않는 잠재 요인입니다.** 모델이 못 보는 이탈 원인이므로, 유형 없음 고객의 설문에서만 두드러지게 나타나야 합니다(§3).
5. **재현 가능해야 합니다.** 구독 ID와 설문 ID로 난수 시드를 고정해, 같은 입력이면 같은 응답이 나옵니다.

### 2.2 숨은 신규 주제 `[제안]`

**유형 10개에 포함되지 않았지만 리뷰에서 반복된 주제**를 숨은 주제로 심습니다. 이전 설계의 T-A(케어 품질)와 T-B(영업 권유)는 확정 유형 T05·T08이 되어 숨은 주제에서 빠지고, 팀이 의도적으로 뺀 두 주제를 쓰는 안입니다. `synth_truth_topic`에 저장하고(검증 전용, 모델 학습·추론 입력 금지) 후보 생성이 복원하는지 확인합니다.

| 주제 | 리뷰 근거 | 설문에서 드러나는 곳 | 비고 |
|---|---|---|---|
| H-A 가입 시 설명·서비스 범위 불일치 | 26건 | motive=`default`, gap=`below`(`gap` 문항의 "가입 후에 알게 된 내용이 많았어요"), issues=cost 또는 exit, idle 이유의 "기대와 달랐어요", 자유 서술 | 기존 유형 6(구독 조건 정보 부족)과 가까움. 삭제한 유형이라 설문에서만 읽음 |
| H-B 케어 가치 불신·자가관리 대체 | 21건 | motive=`care` + gap=`below`, issues=idle 또는 cost, after=`keep`(쓰던 제품 계속 사용)·`buy`, 자유 서술 | 설문에 전용 보기가 없어 위 조합과 주관식으로 드러남 |

- 결합조건 부담(5건)은 건수가 적어 구독료(T01) 심화 문항의 "못 받은 할인" 보기로 흡수하고 숨은 주제에서는 뺐습니다.
- **이 선택은 `[팀 결정 필요]`입니다.** 팀이 "이탈 방지 조치로 풀기 어렵다"고 제외한 주제를 숨은 주제로 쓰는 것이라, 피드백 루프(설문 → 신규 유형 후보 → 관리자 승인)의 시연 소재로 의미가 있지만 제외한 의도와 충돌하지 않는지 확인이 필요합니다.
- 숨은 주제가 실제로 이탈에 영향을 주려면 **데이터 생성 단계에서 숨은 주제 보유 고객의 이탈 확률을 높여야 합니다**(예: 보유 고객의 이탈 로그오즈 +0.8 `[가정]`, `[확정]` 2026-10-06). 관측 피처에는 흔적이 없거나 약해야, 모델이 유형을 못 찾는 "유형 없음 + 위험도 MID 이상"이 나옵니다.

설문의 "받은 조치 / 원했던 해결 방법" 보기(9개)와 **솔루션 시트(v3)의 솔루션**을 연결하는 표입니다. 솔루션 38건이 확정되어(2026-10-07) **확정 솔루션 ID로 갱신**했습니다. 두 가지 일을 합니다. ① 합성 응답에서 `action_log`의 솔루션을 설문 보기로 바꿀 때 씁니다. ② **솔루션 목록에 빠진 것이 없는지 점검하는 체크리스트**로 씁니다. 설문 보기에는 있는데 시트에 대응 솔루션이 없으면 그 보기는 **솔루션 목록에 추가할 후보**입니다 `[제안]`.

**반대 방향 공백(2026-10-09 갱신)** `[팀 결정 필요]`: Agent가 고를 수 있는 솔루션은 33개(`S-NT-A` 제외, `S-T04-D`·`S-T07-C` 비활성화 반영)입니다. 위 표에 대응하는 것은 15개이고, **18개는 대응하는 설문 보기가 없습니다**: `S-T01-A`, `S-T01-B`, `S-T02-B`, `S-T03-A`, `S-T04-A`, `S-T04-C`, `S-T05-A`, `S-T05-B`, `S-T06-B`, `S-T07-A`, `S-T07-B`, `S-T08-A`, `S-T08-B`, `S-T09-A`, `S-T09-B`, `S-T09-C`, `S-T10-A`, `S-T10-B`. 대부분 정보 안내·상담 연결·내부 조치라 9개 보기(일정 재조정, 무상 방문, 요금 감면 등)에 들어맞지 않습니다. 조치 후 설문(`post_action`)의 "받은 조치"를 합성할 때 이 18개는 고를 보기가 없으므로, ① 설문에 "안내·정보를 받음"(`info`) 같은 보기를 더하거나 ② 대응이 없으면 `etc`로 기록하는 규칙 중 하나를 정해야 합니다. 결정 전까지 합성기는 ②로 둡니다 `[제안]`.

"새로운 방법"(`newsol`)도 같은 방식으로 점검합니다: 방문 일정 실시간 알림 ← `S-T06-A`, 수리 중 대체 제품 대여 ← `S-T10-D`, 담당 매니저 지정 ← `S-T07-D`, 약정 중 제품 교체 ← `S-T03-B`, **위약금 단계별 감면과 이용 일시정지는 확정 카탈로그에도 대응이 없음**. 이 둘을 카탈로그에 추가할지는 `[팀 결정 필요]`. 대응이 없는 보기로 응답한 고객이 많다는 결과는 "솔루션 목록이 고객이 원하는 해결 방법을 덮지 못한다"는 신호로 EDA에서 보여 줍니다(§7).

| 새 문항 `channel` | **"이용 관련 안내를 받는다면 어떤 방식이 편하세요?"**(복수 선택: talk 카카오 알림톡, sms 문자, push 앱 푸시, mail 이메일, call 전화·상담원, none 받고 싶지 않음) | 현업 의견(푸시 효과 낮음, 알림톡이 가장 많이 읽힘) 보강. 만족 응답자(`sat`)도 답함 |
| 유지한 것 | 가입 이유 "구독인 줄 몰랐어요"(motive=`default`)와 그 후속 `gap`, idle 이유의 `hassle`·`gap`, 해지 고민의 "방문 관리의 장점", 솔루션 관련 보기(받은 조치·원했던 방법·새로운 방법) | 삭제된 유형은 숨은 원인 탐색용으로 유지(결정). 솔루션 보기는 솔루션 확정 후 수정 |

## 3. 응답 합성 절차

한 구독에 대해 아래 순서로 진행합니다. 모든 단계의 난수는 시드로 고정합니다.

### 3.1 단계 A: 설문 대상·응답 여부

| 설문 종류 | 대상 | 응답률 `[가정]` |
|---|---|---|
| `post_action` | 조치 확정(`조치완료`) 구독 | 잔류 15~20% |
| `post_churn` | 조치 후에도 해지 접수 | 이탈자 25~35% |
| `no_type` | 유형 없음 + 위험 MID 이상 | 잔류 15~20% |
| `no_candidate` | 유형은 있으나 조건에 맞는 후보가 0건이라 만족도 조사로 대체된 구독(2026-10-08 추가, `agent_design.md` §4.8) | 잔류 15~20% |
| `survey_only` | LOW 순위 20~30% 자동 추천 및 수동 발송 | 잔류 15~20% |

- 응답하지 않으면 `survey_send`만 남기고 `survey_response`는 만들지 않습니다.
- **중도 이탈**: 응답을 시작한 사람 중 15%는 중간에 멈춥니다. 멈추는 위치는 심화·자유 서술 쪽이 많도록 문항 순서에 비례해 뽑습니다 `[가정]`. 이 응답은 `completed_yn='N'`으로 저장하고 후보 생성에서는 완료분만 씁니다 `[제안]`.
- 선택 문항은 건너뛰기가 가능하므로 문항당 5%를 건너뜀 처리합니다.

### 3.2 단계 B: `status` (현재 구독 상태)

| 조건 | done | ing | think | sat |
|---|---|---|---|---|
| 해지 접수 이후(`post_churn`) | 50% | 50% | - | - |
| 해지 접수 전, 위험 HIGH | - | - | 80% | 20% |
| 해지 접수 전, 위험 MID | - | - | 60% | 40% |
| 해지 접수 전, 위험 LOW | - | - | 20% | 80% |

`sat`을 고른 응답자는 설문 시안대로 불편·해결·이용 방식 구간을 건너뛰고 생활 환경(`ctx`)으로 갑니다. 합성기도 같은 건너뛰기 규칙을 따라 해당 문항 응답을 만들지 않습니다.

### 3.3 단계 C: `issues` (불편했던 일, 복수 선택)

1. **선택 개수 k**: 1개 50% / 2개 35% / 3개 15% `[가정]`. 활성 유형이 하나도 없고 숨은 주제도 없는 고객은 `none`(불편 없음) 50%, 나머지는 k를 위 분포로 뽑습니다.
2. **각 선택의 출처**를 k번 뽑습니다.

| 출처 | 확률 | 고르는 방법 |
|---|---|---|
| 자기 유형 | 60% | 활성 유형(`activation_strength ≥ 0.3`) 중 강도에 비례해 뽑고 §2.1 가중치로 보기 코드 결정 |
| 다른 기존 유형 | 10% | 비활성 유형 중에서 뽑되 헷갈리는 쌍(§2.1)을 3배 가중하고 §2.1로 코드 결정 |
| 숨은 신규 주제 | 20% | 보유한 숨은 주제가 있으면 그 주제(§2.2)가 정한 불편 코드(H-A → cost 또는 exit, H-B → idle 또는 cost), 없으면 아래 재배분 |
| 기타 | 10% | `other`와 짧은 직접 입력 문구 |

3. **재배분**: 활성 유형이 없으면 자기 유형 몫(60%)을 숨은 주제 보유 시 숨은 주제에, 아니면 다른 기존 유형에 넘깁니다. 숨은 주제가 있는 고객은 숨은 주제 몫이 기본 20%에서 40%로 올라갑니다 `[가정]`. 이렇게 하면 "유형 없음" 설문에 숨은 주제가 집중됩니다. 숨은 주제가 **없는** 고객은 숨은 주제 몫(20%)을 다른 기존 유형에 넘겨 자기 유형 몫이 60%로 유지됩니다 `[가정, 2026-10-09 구현 시 확정]`. 숨은 주제 보유 시 나머지 출처는 같은 비율로 줄여 합이 100%가 되게 합니다.
4. 중복 코드는 한 번만 셉니다.
5. `top`(가장 불편한 일): 선택이 2개 이상일 때만 묻습니다. 자기 유형 중 강도가 가장 높은 쪽 코드를 70%로 고르고, 나머지는 균등합니다.

### 3.4 단계 D: `form` (불편함의 모습)

`top` 코드와 관련한 이벤트 건수를 센 뒤:

| 조건 | 응답 |
|---|---|
| 해당 이벤트 2건 이상(또는 반복 플래그 Y) | repeat 반복 70% / once 20% / fade 10% |
| 해당 이벤트 1건 | once 60% / repeat 25% / fade 15% |
| 해당 이벤트 0건, 또는 idle 계열(사용량 감소) | fade 70% / once 15% / repeat 15% |

해당 이벤트 건수는 코드별로 다음 피처를 씁니다(`[제안]`, 신규 신호는 `churn_types_10.md` §3): visit → `visit_delay_cnt_365d + visit_cancel_cnt_365d + visit_noshow_cnt_365d`, fail → `as_cnt_365d`, care → 케어 후 14일 내 A/S 접수 횟수 + 케어 결과 불만 접수 건수, manager → 담당자 교체 횟수 + 태도 불만 상담 건수, cs → `unresolved_voc_cnt + repeat_voc_cnt`, sales → 방문 중 영업 권유 횟수, cost → `voc_fee_cnt_90d`, exit → `voc_penalty_cnt_90d + voc_cancel_cnt_90d`, renew → `voc_renewal_cnt_90d`, idle → 사용량 추세(건수 0으로 취급).

### 3.5 단계 E: 심화 문항 `deepA`, `deepB`

`top` 코드가 `other`이면 심화 문항을 묻지 않습니다. `visit`은 deepA가 `0`, `idle`은 deepA가 `daily`면 deepB를 건너뜁니다(시안의 SKIPB 규칙). **관측 데이터로 정하는 항목에는 데이터 원천을 표기했습니다.**

| top 코드 | 문항 | 응답 결정 규칙 |
|---|---|---|
| cost | A 구매 대비 비싸다고 느낀 정도 | T01 강도 ≥ 0.7 → p31 / 0.4~0.7 → p30 / 그 외 p10. 10%는 DK로 대체 |
| cost | B 가장 부담스러운 점 (**v2 신규**) | promo: `billed_change_rate_3m` > 0이거나 `promo_days_to_end` ≤ 0(프로모션 종료 후) → 40% / missed: 미적용 할인 신호(신규 피처) 있음 → 35% / total 25% / fixed 나머지 / other 5% |
| exit | A 가장 어려운 부분 | `voc_penalty_cnt_90d` > 0 → pen 55% / `voc_move_cnt_90d` > 0 또는 `region_changed_flag` → reinst 50%·rm 25% / 그 외 wait·other |
| exit | B 추가로 낸 비용 | 예상 위약금 = 월 요금 × 잔여 개월 × 구간 비율(1년차 30% 등 `penalty_zone` 기준)로 구간 환산: 0 / 10만 미만 / 10~30만 / 30만 이상. 해지 전(`think`)이면 "0" 비중을 높게(60%) |
| renew | A 가장 불편한 점 (**v2 신규**) | newmodel: 신모델 출시 여부(신규 피처) → 35% / eol: `model_discontinued_yn` = Y → 50% / push: 재계약 안내 접촉 횟수(신규 피처) ≥ 2 → 45% / price 나머지 / other 5% |
| renew | B 제안에 대한 행동 | `status`가 done·ing면 switch 35%·refuse 35%, think면 think 45%·accept 20% |
| idle | A 최근 3개월 사용량 | 주간 가동 횟수 평균 ≥ 6 → daily / 2~6 → week / 0.25~2 → month / < 0.25 → rare. 단 설문 응답자가 `idle`을 고른 것이므로 daily는 20% 이하로 제한 |
| idle | B 쓰지 않게 된 이유 | T04 활성 → noneed 40%·season 30%·hassle 10%·gap 10%·other 10% / H-A 보유 → gap 50% / 그 외 균등 |
| care | A 겪은 문제 | 케어 후 14일 내 A/S 접수 ≥ 1 → dmg 50%·clean 25%·skip 20% / 없음 → clean 40%·skip 35%·dmg 15%·other 10% |
| care | B 재방문·보상 | none 50% / part 30% / full 20% |
| visit | A 지연·취소·조율 어려움 횟수 | `visit_delay_cnt + visit_cancel_cnt`(365일)를 0/1/2/3+로 환산. 일정 조율 어려움 위주 응답자(예약 대기일 길거나 평일 낮 방문 어려움)는 1~2로 둠 |
| visit | B 가장 오래 미뤄진 기간 | `completed_date − scheduled_date` 최댓값을 1주 이내/2주/1개월/1개월 이상으로 환산 |
| manager | A 불편한 점 | 태도 불만 상담 건수 ≥ 1 → attitude 55%·privacy 15% / 담당자 교체 횟수 ≥ 2 → skill 55% / 그 외 attitude 40%·skill 35%·privacy 10%·other 15% |
| manager | B 담당자 변경 횟수 | 실제 담당자 교체 횟수(신규 피처)를 0/1/2/3+로 환산, 기록이 없으면 DK 10% |
| sales | A 영업 권유 횟수 | 방문 중 영업 권유 횟수(신규 피처)를 1번/2~3번/4번 이상으로 환산, 없으면 1번 30%·2~3번 45%·4번 이상 25% |
| sales | B 거절 후 상황 | 거절 후 재권유 여부(신규 피처)가 Y면 keep 70% / 그 외 keep 40%·unsaid 30%·stop 30% |
| fail | A 문제 종류 | `symptom_code`를 noise/perf/broken로 묶은 매핑(코드표 확정 필요 `[가정]`) |
| fail | B 반복 횟수 | `repeat_symptom_cnt_90d` 또는 `as_cnt_365d`를 once/2/3+로 환산 |
| cs | A 불편한 점 | A/S 분리 접수(신규 피처) = Y → split 50% / `response_hours_avg` 높음 → slow 40%·blame 30% / 그 외 균등 |
| cs | B 접수~해결 소요 | `repair_days` 또는 `response_hours`로 3일/7일/14일/15일 이상 환산, `unresolved_voc_cnt > 0`이면 open 25% |

DK("잘 모르겠어요", "기억나지 않아요")는 각 문항에서 5~10%를 무작위로 대체합니다.

**구현 시 정한 세부 `[가정, 2026-10-09]`** (`feedback/deep.py`, 값은 `config.yaml`의 `deep:`)
- 입력은 `Subject.facts`(피처 이름 → 값). 값이 없으면 해당 문항은 기본 분포(균등 또는 표의 "그 외" 열)로 합성합니다.
- 조건이 여러 개 겹치는 표(cost B, renew A)는 지정한 확률을 그대로 주고 남은 몫을 기본 보기(fixed·price)에 줍니다. 남은 몫이 너무 작으면 최소 10%를 두고 합이 1이 되게 정규화합니다. exit A에서 위약금과 이사 신호가 겹치면 두 분포의 평균을 씁니다.
- `idle` A는 `daily`를 20% 이하로 제한합니다(나머지는 `week`로 내림). `visit` A에서 일정 조율 어려움 응답자는 1~2로 한정합니다.
- 해지 전(`think`)의 exit B는 데이터 구간과 상관없이 60%를 "0"으로 둡니다. 그래서 데이터 일치율 검사(≥95%)는 해지 후 응답에서만 적용합니다.
- fail B는 `as_cnt_365d`를 쓰고 없으면 `repeat_symptom_cnt_90d + 1`을 씁니다. fail A의 증상 코드 묶음(SYM01~04 noise, 05~08 perf, 09~12 broken)은 `data_schema_design.md`의 증상 코드표 `[제안]`를 따릅니다(생성기는 그대로, 팀 확인 필요).
- DK는 보기에 DK가 있는 문항만 대체합니다. cost A는 10%, 그 외는 문항마다 5~10%에서 뽑은 확률입니다. manager B는 교체 기록이 없으면 DK 10%를 더합니다.

### 3.6 단계 F: 해지 고민·해결 경험

| 문항 | 규칙 |
|---|---|
| `hesitate` (복수) | pen: T02 활성이거나 해지 접수 시 `penalty_zone` 1~2년차 → 50% / pick: 대형가전 → 30% / habit: 기본 25% / term: `days_to_end > 180` → 40% / visit: 방문형 케어 → 35% / none: 20%. `none` 선택 시 다른 항목은 비움 |
| `action` (마지막 조치) | `action_log`에 `조치완료`가 있으면 그 솔루션을 §2.5로 환산. 없으면 `no` 55% / `never` 45%. 불편이 없으면 묻지 않음 |
| `helped` | 조치가 있을 때만. 아래 §3.7 적합도 표 |
| `why` | `helped`가 part/little/worse일 때만. 복수 선택(1~2개): late(T06·T10 활성 시 가중), mismatch(적합도 불일치), again(T09 활성), diff(T07·T10 활성), unclear(T02 활성 또는 H-A 보유), promise(기본 10%), other 5% |
| `wanted` | `top` 코드의 §2.3 매핑(주 60%·부 40%). 20%는 `hard`(어떤 방법으로도 어려움) 또는 무작위 보기로 대체 |
| `newsol` (복수) | `issues`에 포함된 코드마다 §2.4 매핑 보기를 60% 확률로 선택, 15%는 `none` |

**구현 시 정한 세부 `[가정, 2026-10-09]`** (`feedback/stage_f.py`, 값은 `config.yaml`의 `stage_f:`)
- `hesitate`: 항목마다 독립적으로 뽑습니다. 조건이 맞으면 표의 확률, 맞지 않으면 낮은 기본값(pen 10% / pick 5% / term 10% / visit 5%, habit은 25% 고정)을 씁니다. `none`을 고르거나 아무것도 못 고르면 `none`만 남깁니다. `pen`의 "해지 접수 시 1~2년차"는 `post_churn`일 때만 적용합니다.
- `action`: `Subject.action_solution`이 없으면 `no` 55% / `never` 45%. 솔루션이 설문 보기 둘에 대응하면(`S-T06-D`) 주 70% / 부 30%로 기록합니다.
- 적합도(§3.7): 솔루션 ID의 유형(`S-T06-A` → T06)이 고객의 **가장 강한 활성 유형**이면 정확, **다른 활성 유형**이면 부분, 활성 유형이 아니거나 유형 없음 솔루션이면 불일치입니다.
- `why`: 1개 60% / 2개 40%, 항목별 기본 가중(late 15, mismatch 10, again 5, diff 5, unclear 5, promise 10, other 5)에 조건 가산을 더해 중복 없이 뽑습니다(late +35, mismatch +40(불일치)·+15(부분), again +40, diff +30, unclear +30).
- `wanted`: `top`을 건너뛴 응답은 첫 불편 코드 기준, `other`는 대응표가 없어 hard 또는 무작위입니다. 20% 대체분은 hard 50% / 무작위 보기 50%입니다.
- `newsol`: 15%는 `none`. 아니면 불편 코드별 대응 보기를 60%씩 고르고 하나도 없으면 `none`. 불편 `other`는 `newsol=other`를 40%로 고릅니다.
- 설정 파일의 YAML 키 `no`는 불리언(False)으로 읽히는 문제가 있어 따옴표로 감쌌고, 같은 사고를 막는 테스트를 넣었습니다.

### 3.7 `helped` 적합도 표 `[가정]`

조치 솔루션이 고객의 유형과 얼마나 맞는지에 따라 정합니다. 기준은 `overall_pipeline.md` §3.3의 적합도(정확 / 부분 / 불일치)와 같습니다.

| 적합도 | solved | part | little | worse |
|---|---|---|---|---|
| 정확 대응 | 50% | 30% | 15% | 5% |
| 부분 대응 | 25% | 35% | 30% | 10% |
| 불일치 | 8% | 22% | 50% | 20% |

`post_churn`(조치 후에도 해지 접수) 응답은 위 확률에서 solved를 절반으로 줄이고 little·worse로 넘깁니다. 조치 후 이탈이 남았다는 사실과 설문이 일관되게 하기 위함입니다.

### 3.8 단계 G: 이용 방식, 생활 환경, 주관식

| 문항 | 규칙 |
|---|---|
| `motive` | 기본 분포: cost 20 / care 20 / new 10 / promo 20 / move 10 / recom 10 / other 5 / default 5(%). H-A 보유 시 default 70% 이상, H-B 보유 시 care 60% 이상. T04 활성은 care·new 쪽으로 약간 이동 |
| `gap` | `motive=default`이면 "구독 조건이 가입 때 알던 것과 어땠나": H-A 보유 시 below 80%, 그 외 same 50%. 그 외 motive이면 "기대 대비": H-B 보유 시 below 70%, 활성 유형 최대 강도 ≥ 0.6 → below 55%, 아니면 same 50%·over 25% |
| `firstact` | VOC 주 채널(전화/앱/챗봇) 기준: 전화 → call, 앱·챗봇 → app, VOC 없음 → wait 45%·search 25%·self 15% |
| `research` (복수) | penalty: T02 활성 / compare: T01 활성 / ask: VOC 있음 / agency: T07·T10 강도 ≥ 0.7이고 미해결 → 15% / review: 기본 30% / none: 25% |
| `after` | status가 done·ing면 buy 25 / sub 20 / keep 10 / used 20 / none 10 / unsure 10 / other 5, T04 활성이면 none 가중, T01 활성이면 sub·used 가중, T02(이사) 활성이면 sub 가중, H-B 보유 시 keep·buy 가중 `[가정]`. think면 unsure 비중을 크게 |
| `ctx.hh` | 고객 속성에 가구 형태가 있으면 그 값, 없으면 solo 35 / couple 20 / baby 15 / kid 20 / other 10 |
| `channel` (복수, **v2 신규**) | 기본 선택 확률 talk 65 / sms 45 / push 15 / mail 15 / call 20 / none 8(%), 1~3개 선택 `[가정]`. 고연령 속성이 있으면 sms·call 가중. `none`을 고르면 다른 항목은 비움. **현업 의견(푸시 효과 낮음, 알림톡이 가장 많이 읽힘)을 시작값에 반영한 합성 가정**이라 채널 효과를 입증하는 자료가 아니며, 시연에서는 "설문 응답 예시"로만 씀 |
| `ctx.daytime` | T06 활성이면 rare 가중, 아니면 most 40 / some 40 / rare 20 |
| `ctx.exp` | `tenure_months`가 길고 다른 가전 구독이 있으면 more, 기본 first 55 / more 30 / past 15 |
| `ctx.who` (sat 제외) | 상담원 해지 문의 기록이 있으면 agent 가중, 기본 self 55 / family 20 / famreq 10 / review 10 / agent 5 |
| `interview` | yes 15% (불편 강도가 높을수록 가중). yes일 때 연락처는 가상 문자열(`dummy-0001@example.test`) |
| `open` | 아래 §3.9 |

**구현 시 정한 세부 `[가정, 2026-10-09]`** (`feedback/stage_g.py`, 값은 `config.yaml`의 `stage_g:`)
- `motive`: H-A와 H-B를 둘 다 가지면 default 40% / care 40%로 나눕니다. 한쪽만 가지면 그 보기의 몫을 70%(default)·60%(care)로 고정하고 나머지는 기존 비율대로 나눕니다. T04 활성이면 care·new를 1.5배 합니다.
- `gap`: 활성 유형 최대 강도 ≥ 0.6이면 below 55% / same 30% / over 15%, 그 외는 same 50% / over 25% / below 25%. `motive=default`의 그 외는 same 50% / below 30% / over 20%.
- `research`: 조건이 맞는 항목(T02·T01 활성, VOC 있음)은 60%, 아니면 5%. `agency`는 조건 충족 시 15%, 아니면 0. `none`을 고르거나 아무것도 못 고르면 `none`만 남깁니다.
- `after`: T04 활성 `none` ×2, T01 활성 `sub`·`used` ×1.5, T02 활성 `sub` ×1.5, H-B 보유 `keep`·`buy` ×1.5. `think`이면 `unsure`를 40%로 고정합니다.
- `channel`: 개수 1/2/3개를 40/40/20%로 정하고 기본 선택 확률에 비례해 중복 없이 뽑습니다. `none`이 뽑히면 `none`만 남깁니다. 고연령 속성(`senior_yn`)이면 sms·call ×1.5.
- `interview`: 확률 = 15% × (0.5 + 최대 활성 강도). 강도 1.0이면 22.5%, 0이면 7.5%.
- `firstact`: VOC가 있으면 채널로 정해지고(전화 → call, 앱·챗봇 → app), 없으면 wait 45 / search 25 / self 15 / tech 10 / other 5(%).
- 입력(`Subject.facts`) 키: `household`, `voc_cnt`, `voc_channel`, `unresolved_voc_cnt`, `tenure_months`, `other_subs_cnt`, `senior_yn`, `agent_inquiry_yn`, `large_appliance_yn`, `days_to_end`, `visit_care_yn`, `penalty_zone`. 없으면 기본 분포를 씁니다.

### 3.9 주관식(`open`)

- **작성 여부**: 응답 완료자 중 55%가 작성, 나머지는 비웁니다 `[가정]`.
- **생성 방식** `[제안]`: **문장 풀 샘플링**이 기본이고, LLM은 **풀을 만들 때 오프라인에서 한 번만** 씁니다. 이유는 시연 중에는 호출 비용·지연·결과 변동이 없어야 하고, 사용한 문장 목록을 팀이 검토·확정할 수 있어야 하기 때문입니다.
  1. 코드(불편 코드 10개와 숨은 주제 H-A·H-B, 총 12개)마다 사람이 쓴 시드 문장 3~5개를 만듭니다.
  2. 이를 LLM에 주고 문체·표현을 바꾼 변형 문장을 코드당 20~30개 생성합니다(전체 약 250~350문장, 호출은 코드별 1회씩 12회 안팎).
  3. 팀이 검토해 부적절한 문장(개인정보 형태, 과장, 코드와 안 맞는 내용)을 빼고 `sentence_pool.yaml`에 확정합니다.
  4. 시연·합성 중에는 풀에서만 뽑고, LLM을 호출하지 않습니다.

  이 방식이면 LLM 비용은 문장 풀을 만들 때 한 번 드는 소량이고, 문장 목록이 파일로 확정됩니다. 풀 생성 프롬프트의 입력·출력 예시는 구현 때 정합니다.
- **길이**: 0~500자, 평균 60자 안팎. 짧은 문장 70% / 2~3문장 25% / 긴 글 5%.
- **금지**: 실명, 연락처, 구독번호, 주소 등 개인정보 형태의 값을 문장에 넣지 않습니다.
- **풀 예시** (코드당 일부):

| 코드 | 예시 문장 |
|---|---|
| visit | "방문 일정이 계속 바뀌어서 그날 일정을 다 비워 뒀는데 허탕을 쳤어요." |
| fail | "같은 증상으로 세 번째 접수인데도 고쳐지지 않습니다." |
| cost | "구매하는 게 더 싸다는 걸 계산해 보고 알았어요." |
| care | "점검 오셨는데 10분 만에 가시고 필터는 그대로였어요." |
| sales | "점검 중에 다른 제품 교체를 계속 권해서 불편했습니다." |
| default (H-A) | "구매하려고 봤는데 월 요금만 크게 보여서 구독인 줄 몰랐어요." |
| 케어 가치 불신 (H-B) | "필터는 제가 직접 갈아도 되는데 케어비를 계속 내는 게 아깝다는 생각이 들었어요." |

**구현 결과 `[2026-10-09]`**
- 문장 풀 키는 15개입니다: 불편 코드 10개, 숨은 주제 H-A·H-B, `sat`(불편 없음·만족 응답자), `other`(top이 기타), `issue_other`(issues에서 기타를 고른 사람의 짧은 직접 입력 문구). 시드 문장은 코드당 4개(`issue_other`는 5개)를 `feedback/sentence_pool.yaml`에 넣었습니다.
- 주관식 작성은 **끝까지 응답한 사람** 중 55%이고 문항 건너뜀 5%가 따로 적용됩니다. 숨은 주제를 가진 사람은 50% 확률로 그 주제의 문장을 씁니다. 만족(`sat`)이거나 불편이 없는 사람은 `sat` 문장, 그 밖에는 `top` 코드 문장입니다.
- 변형 문장은 `scripts/build_sentence_pool.py`가 LLM을 코드당 1회 호출해 **후보 파일**(`sentence_pool_variants.candidate.yaml`)로 만듭니다. 팀이 검토해 승인한 문장만 `sentence_pool_variants.yaml`의 `variants:` 아래로 옮기면 합성기에 반영됩니다. 후보 파일은 합성기가 읽지 않습니다. 문장마다 전화·이메일·주민번호·URL·내부 필드명 형태와 길이를 검사합니다.

## 4. 저장 형식 `[제안]`

설문 응답은 문항·보기가 바뀌어도 테이블을 바꾸지 않도록 **long 형식**으로 저장합니다.

| 테이블 | 주요 컬럼 | 설명 |
|---|---|---|
| `survey_send` | survey_id PK, subscription_id, survey_type(post_action/post_churn/no_type/no_candidate/survey_only), sent_at, sent_by(auto/manual), responded_yn | 발송 이력 |
| `survey_response` | response_id PK, survey_id, completed_yn, status_code, submitted_at | 응답 단위(응답 1건 = 1행) |
| `survey_answer` | response_id, question_id, answer_code, other_text | 문항·보기 단위. 복수 선택은 여러 행, 주관식은 `other_text` |
| `synth_truth_topic` | subscription_id, topic_id, strength | 숨은 주제(검증 전용, 학습·추론 입력 금지) |

`question_id`와 `answer_code`는 설문 시안의 코드(`issues`, `cost`, `exit` 등)를 그대로 씁니다. 설문 문항이 확정 변경되면 코드표만 갱신하면 됩니다. 기존 `survey_send` / `survey_response` 설계(`data_schema_design.md`)와의 컬럼 차이는 SQL 반영 때 맞춥니다 `[팀 결정 필요]`.

## 5. 검증 방법

합성기가 의도대로 동작하는지, 그리고 후보 생성이 숨은 주제를 복원하는지 따로 확인합니다.

| 검사 | 기준 |
|---|---|
| 건너뛰기 일관성 | `sat`에서 불편·해결·이용 방식 문항 응답이 0건. `visit=0`·`idle=daily`일 때 deepB 없음 등 시안의 모든 skip 규칙 위반 0건 |
| 데이터 일치 | 방문 지연 횟수 응답이 이벤트 테이블 값과 구간 일치율 ≥ 95%(DK 제외) |
| 유형↔불편 코드 혼동 행렬 | **선택 1회당** 자기 유형 출처 비율 ≈ 60%±10%p(설정값 주변). 응답 단위 포함률은 선택이 여러 번이라 이보다 높음(활성 유형 1개 기준 약 73%) `[구현 시 정정 2026-10-09]` |
| 숨은 주제 분포 | 숨은 주제 응답이 "유형 없음 + MID 이상" 설문에서 일반 설문보다 2배 이상 많음 |
| 응답률·완료율 | 설정값 ±3%p |
| 재현성 | 같은 시드 → 응답 완전 동일 |
| 후보 생성 복원 | 심은 숨은 주제 2개(H-A, H-B)가 모두 후보로 나타남(구현 후, `[가정]`) |

## 7. 관리자 설문 집계 화면 (EDA) `[제안]`

설문이 쌓인 뒤 관리자가 한눈에 보고 판단할 수 있도록, 집계를 **그래프 중심의 탐색 화면**으로 만듭니다. 응답은 합성 데이터라 화면 상단에 "가설 기반 합성 응답" 표시를 항상 둡니다.

**공통 필터** (모든 차트에 적용): 설문 종류(`post_action`·`post_churn`·`no_type`·`no_candidate`·`survey_only`), 위험 등급, 이탈 유형, 제품군, 완료 응답만 보기.

| 구역 | 차트 | 보는 것 | 읽는 법 |
|---|---|---|---|
| ① 응답 현황 | 발송 → 응답 → 완료 **깔때기 막대**, 설문 종류별 응답률 막대 | 응답이 충분히 모였는가 | 응답 수가 적은 구간은 아래 차트의 신뢰도가 낮다고 안내 |
| ② 불편의 종류 | 불편했던 일(`issues`) **가로 막대**(복수 선택 합산), 가장 불편했던 일(`top`) 막대 | 고객이 말하는 불편의 순위 | 막대 길이 = 응답자 중 해당 보기 선택 비율 |
| ③ 유형과 응답 비교 | **히트맵**: 행=모델이 부여한 이탈 유형, 열=설문 불편 코드, 값=비율 | 모델이 본 유형과 고객이 말한 불편이 일치하는가 | 대각선(1:1 대응 유형)이 진하면 일치. 대각선 밖이 진한 칸은 헷갈리는 유형 쌍(§2.1). **유형에 안 맞는 응답(`other`, motive=`default`, gap=`below`)이 몰리는 곳은 "숨은 신규 주제" 신호** |
| ④ 유형 없음 집중 분석 | "유형 없음 + MID 이상" 응답만 모은 불편 코드 막대, 일반 응답과 비교 | 모델이 못 본 불만이 무엇인가 | 일반 응답에서 적고 이 그룹에서 높은 코드 = 신규 유형 후보 |
| ⑤ 조치 효과 | 받은 조치(`action`)별 도움 정도(`helped`) **누적 막대**, 적합도(정확·부분·불일치)별 비교 | 어떤 조치가 도움이 됐는가 | solved 비율이 낮은 솔루션은 개선 대상 |
| ⑥ 부족했던 이유 | `why` 막대 | 도움이 안 된 이유 | late·diff 등 이유별로 개선 방향 구분 |
| ⑦ 원하는 해결 방법 | 원했던 방법(`wanted`)과 실제 받은 조치(`action`) **교차 히트맵** | 고객이 원한 것과 준 것의 간극 | 간극이 큰 칸 = 솔루션 목록 보완 후보. 카탈로그 대응이 없는 보기는 별도 색으로 표시(§2.5) |
| ⑧ 새로운 방법 | `newsol` 막대 | 도입하면 좋을 새 솔루션 | 응답이 많은 것부터 신규 솔루션 후보 |
| ⑨ 이용 방식 | 가입 이유(`motive`), 기대 대비(`gap`), 해지 후 계획(`after`) 막대 | 가입 동기와 이탈 후 행동 | `motive=default` + `gap=below` 비율이 높으면 H-A, `motive=care` + `gap=below` + after=`keep`이 높으면 H-B 신호 |
| ⑩ 해지 고민 요인 | `hesitate` 막대 | 해지를 망설이는 이유 | 위약금·약정·수거 부담 비중 |
| ⑪ 주관식 | 주제별 문장 수 막대, 대표 문장 목록 | 주관식에서 반복되는 주제 | 후보 생성(군집화) 결과 화면으로 연결 |
| ⑫ 안내 채널 | `channel` 선택 비율 막대, 이탈 유형·연령대별 비교 | 고객이 선호하는 안내 방식 | 알림톡·문자 비중. 합성 가정값이라 "현업 의견을 시연에서 설명하는 보조 자료"로만 사용 |

**구현 방식**: `survey_answer`(long 형식)를 `pandas`로 집계하고 `plotly`(또는 `altair`)로 그립니다. 같은 집계를 API(`GET /surveys/summary?survey_type=&risk_level=&type_id=…`)로 제공하고 Streamlit "설문 분석" 탭이 이를 호출합니다. 집계는 질문 코드(`question_id`) 기준이라 설문 문항이 바뀌어도 코드표만 갱신하면 차트가 유지됩니다.

**EDA 노트북** `[제안]`: 같은 집계를 Jupyter 노트북(`eda/survey_eda.ipynb`)으로도 두어, 발표 준비와 팀 내 검토 때 값을 바꿔 가며 볼 수 있게 합니다. 그래프 형태는 구현 단계에서 합성 데이터를 넣어 보고 읽기 쉬운 쪽으로 조정합니다.

### 11.2 2차 OpenAI 실행(수정본)과 2단계 분류 추가 (2026-10-09)
- mini: 후보 5개, 거절 0. "안내·상담 내용 불일치형"(근거 23, 이 중 H-A 보유 11명)이 H-A에 대응(정밀도 47.8%, 재현율 12.0%; 기준선 5.0%). 나머지 4개는 기존 유형(T05·T10·T06·T04) 재서술로, `closest_type_id`·`difference`를 써도 그럴듯한 차이로 합리화함 → 자기 점검으로는 신규성 판단 불충분. H-B는 후보로 못 나옴(보유자 중 H-B 문장 작성 19명이 15개 고유 문장에 흩어져 각 문장 n이 1~2).
- nano: 1차 빈 배열, 재시도에서 2개(둘 다 기존 유형 T06·T07 솔루션 아이디어), H-A·H-B 회수 없음. 이 과제는 mini 이상이 필요해 보임.
- 추가: 선택 기능 `--two-stage`. 1단계 LLM이 문장마다 가장 가까운 기존 유형과 일치 정도(exact/partial/none)를 붙이고, exact 문장을 뺀 나머지만 2단계로 넘김. partial은 `near`(가까운 유형)를 붙여 남김. 분류 실패 시 전체 문장으로 진행. 효과는 재측정 필요.

## 12. 승인 흐름 (`feedback/approve.py`) 구현 `[2026-10-09]`
- 채택: `ai_proposal`(상태 '검토중')만 처리. 새 유형은 `T{최대+1}`(T11~), 솔루션은 `S-T11-A…`(기존 유형에 붙이는 new_solution은 다음 빈 알파벳), `seq_no`는 기존 최대+1부터. `ai_proposal`은 '채택'·reviewed_by·reviewed_at이 채워지고, 새 유형이면 `related_type_id`에 새 유형 ID가 남음(추적용). 검토 기록(결정·메모·생성 ID)은 `evidence_json.review`에 추가.
- **안전장치 `[제안]`**: 채택으로 만든 솔루션은 `active_yn='N'`·`agent_selectable_yn='N'`·`new_policy_yn='Y'`. Rule Engine은 둘 다 'Y'인 행만 쓰므로 사람이 `activate`(내부 전달은 부서 필수, 자격 조건 선택)를 하기 전에는 Agent 출력이 달라지지 않음. 새 유형은 모델이 모르는 유형이라 `churn_prediction_type`에 나오지 않음(재학습·유형 매핑은 별도).
- 기본값(채택 후 사람이 수정): 정보제공·혜택제안 -> 알림톡/고객 메시지(priority 20·30), 담당자조치·제품조치 -> 내부 전달(40), 의견수집 -> 상담·앱(50). `offer_cost` 0, `fee_impact` 없음 — 혜택제안은 비용·요금 영향을 사람이 확인해야 함.
- 거절 조건: 자동 이름("미분류 패턴…")은 `type_name`을 직접 지정해야 채택, 솔루션이 없는 신규 유형 불가, 기존 유형 이름·ID(T##) 사용 불가, 이중 처리 불가, 기각은 사유 필수. 동시 처리는 `FOR UPDATE`로 막음.
- 테스트: 순수 계획(`plan`) 단위 테스트 + PostgreSQL 통합 테스트(채택·이중 채택·미리보기·활성화·기각·무결성 검사 SQL). 전체 485 passed.
- 수정: 기존 유형 ID 검사 정규식이 "T05와"처럼 한글이 붙으면 못 잡던 문제(후보 검증기·승인 모두)를 고침.
