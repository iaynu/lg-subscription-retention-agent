# 02. 데이터 스키마 설계서 (대표본)

> 정본: `data_schema_design.md`(v1.4) · DDL `schema_postgres.sql` · ERD `erd_schema.png`
> 이 문서는 설계 의도와 핵심 구조를 요약합니다. 컬럼 단위 명세와 생성 확률표는 정본을 봅니다.
> 모든 값은 가설 기반 합성 데이터입니다.

---

## 1. 설계 목표

실제 데이터가 없는 상황에서 **(a) 예측 모델, (b) 유형 도출, (c) Agent, (d) 피드백 루프를 모두 끝까지 돌릴 수 있는** 스키마와 데이터를 만드는 것이 목표였습니다. 그래서 두 가지를 동시에 풀어야 했습니다.

- 운영 시스템처럼 보이는 **업무 테이블**(고객·구독·이벤트·예측·조치)
- 검증을 위한 **정답 테이블**(합성 라벨·진짜 유형·숨은 주제)을 업무 테이블과 **완전히 분리**

## 2. 설계 원칙

| 원칙 | 내용 |
|---|---|
| 스코어링 단위 | 구독(subscription). 고객 1 : 구독 1이 MVP이나 구조는 1:N 허용 |
| 기준일 | 단일 시점 스냅샷(예: 2026-09-30). 피처는 기준일까지, 라벨은 이후 30일 내 해지 여부 |
| 누수 방지 | 스냅샷의 `subscription.status`는 전부 '활성'. 정답은 `synth_*` 테이블에만 둠 |
| 피처 미저장 | 원천 테이블에서 `build_features(as_of)`로 계산 |
| 이식성 | PostgreSQL, VARCHAR+CHECK, Y/N은 CHAR(1), 결측은 NULL |
| 외래키 | DB 제약은 두지 않고 논리 관계 29개를 `check_integrity.sql`로 검사(부모 없는 행 수가 모두 0) |
| 조치 | 실제 발송 없이 `action_log`에 이력만 기록 |

외래키를 두지 않은 것은 합성 데이터를 반복해서 다시 만드는 작업 흐름에서 적재 순서와 수정 제약이 비용이 컸기 때문입니다. 대신 PK·UNIQUE·NOT NULL·CHECK는 유지하고 조인 컬럼 인덱스를 직접 만들었습니다.

## 3. 테이블 구성 (약 20개)

| 구분 | 테이블 | 역할 |
|---|---|---|
| 참조 | `product_profile`, `care_manager`, `churn_type`, `solution_catalog` | 제품군 기본값, 매니저, 10개 유형, 솔루션 화이트리스트 |
| 핵심 | `customer`, `subscription` | 고객, 구독(스코어링 단위) |
| 이벤트 | `usage_thinq`, `care_visit`, `voc_contact`, `payment`, `notice_log` | 주간 사용, 점검·AS·설치, 상담·문의, 청구·납부, 안내 발송·열람 |
| 결과 | `churn_prediction`, `churn_prediction_type`, `agent_result`, `action_log` | 점수, 유형별 기여도, Agent 결과(JSON), 확정 조치 이력 |
| 설문 | `survey_send`, `survey_response`, `survey_answer`, `ai_proposal` | 발송, 응답, 문항별 답(long 형식), AI 신규 유형 제안과 검토 상태 |
| 합성 정답 | `synth_churn_label`, `synth_truth_type`, `synth_truth_topic` | 학습 라벨, 검증용 진짜 유형, 설문 합성용 숨은 주제 |

흐름: **Customer → Subscription → 이벤트 → 피처 → ML → churn_prediction(+type) → Rule Engine → solution_catalog 선택 → action_log**

## 4. 핵심 설계 포인트

### 4.1 정답 분리
`synth_*` 테이블은 학습·추론 입력에 쓰지 않습니다. 설문 응답을 만드는 **숨은 주제(H-A, H-B)** 도 이 계층에 두어, Agent가 정답을 미리 아는 일이 구조적으로 불가능하게 했습니다. 이 분리가 "검증을 믿을 수 있는 정도"의 마지노선입니다.

### 4.2 `solution_catalog` — LLM의 선택지를 데이터로 정의
LLM이 고를 수 있는 솔루션을 코드가 아닌 **테이블**로 관리합니다. 주요 컬럼:

| 컬럼 | 역할 |
|---|---|
| `type_id`, `solution_category` | 대상 유형, 구분(정보제공/담당자조치/혜택제안/제품조치) |
| `channel`, `ad_yn` | 알림톡·친구톡·내부 전달·상담/앱, 광고성 여부(광고 동의 고객만) |
| `offer_cost`, `fee_impact` | 회사 추가 부담 금액(비용 상한 판정), 월 요금 변동 방향 |
| `eligibility` (JSON) | 후보 자격 조건. 필수 조건은 값이 없으면 후보 제외 |
| `priority` | 선택 순서(작을수록 먼저) |
| `customer_title`, `message_items` | 알림톡 형식의 제목, ▶ 항목에 쓸 고객 공개 값 키 |
| `agent_selectable_yn`, `active_yn` | 전사 개선 항목 제외, 운영 on/off |

카탈로그는 38건이며, 이 중 전사 개선 3건은 구독자 단위 후보가 아니고 2건은 비활성이라 **Agent가 실제로 고를 수 있는 것은 33건**입니다. 별도로 만족도 조사 `S-NT-A` 1건이 유형 없음·후보 없음 경로의 대체 후보입니다. 솔루션 4가지 구분과 4개 채널(알림톡 24 · 친구톡 6 · LG 내부 전달 12 · 상담·앱 2; 복합 솔루션은 중복 집계)로 구성됩니다.

### 4.3 예측과 유형은 1:N
`churn_prediction`은 구독당 1행(목록 화면용 사전 계산), `churn_prediction_type`은 예측 1건당 유형 1~3행과 기여도를 가집니다. 유형이 없는 고객은 '유형없음' 행으로 표현합니다.

### 4.4 신규 유형의 안전한 등록
`ai_proposal`에서 관리자 승인을 거친 새 유형(T11+)과 솔루션은 `active_yn='N'`, `agent_selectable_yn='N'`으로 시작합니다. 자동 발견이 곧바로 고객 조치로 번지지 않게 하는 스키마 차원의 안전장치입니다.

## 5. 합성 데이터 생성 규칙

핵심은 "정답이 어떻게 만들어졌는지를 내가 알고 있다"는 점을 이용해 **파이프라인이 그 구조를 되찾는지** 확인하는 것입니다.

### 5.1 유형 배정
- 고객의 80%는 정상, 20%는 이탈 위험(활성) 상태입니다.
- 활성 고객의 유형 개수는 1/2/3개가 35/40/25%입니다.
- 유형 선택 확률은 **리뷰 비중 50% + 균등 50%** 혼합입니다(예: T05 20.6%, T07 15.2%, … T04 5.6%). 리뷰 근거가 적은 유형이 아예 사라지지 않게 하기 위함입니다.
- 각 유형의 강도는 U(0.4, 1.0)에서 뽑습니다(T03은 별도 규칙).

### 5.2 라벨 생성식

```
logit = b0 + w_scale × (1.0·c1 + 0.5·c2 + 0.25·c3) + w_timing × max(1 − days_to_end/90, 0) + N(0, 0.5)
P = sigmoid(logit),  churn = (uniform < P)
```

- `c1, c2, c3`: 고객이 가진 유형 1·2·3순위의 **고정 가중치 w × 강도** (w 예: T01 3.5, T03 4.4, T04 2.2)
- 순위 가중 1.0/0.5/0.25: 주 유형이 가장 크게 기여
- `w_timing`: 계약 만료가 가까울수록 위험 상승
- 노이즈 N(0, 0.5): 같은 신호여도 결과가 달라지는 현실성
- 튜닝한 것은 `b0`(−3.4→−4.6)과 `w_scale`(1.5→1.0) **두 개뿐**이며 목표는 전체 이탈률 약 8%입니다.

시뮬레이션(N=200,000)에서 전체 8.0%, 활성군 35.7%, 정상군 1.1%였고, 실제 생성 데이터는 8.3% / 37% / 1.1%입니다. (표본·시드 차이로 8.0% 대 8.3%가 함께 나옵니다.)

### 5.3 유형별 신호 행렬
유형마다 "어떤 이벤트·속성이 어떻게 달라지는가"를 정의했습니다(예: T06 방문 일정 불편 → 일정 변경·재방문 증가, T01 구독료 부담 → 납부 지연·요금 문의). 유형 간 혼동 쌍(T05↔T07 등)도 일부러 겹치게 해 분류가 쉬워지지 않게 했습니다.

## 6. 검증 방법

- 적재 후 `check_integrity.sql` — 논리 관계 29개, 고아 행 0
- 생성된 이탈률·유형 분포를 설계값과 비교
- 파이프라인 단계에서 정답 복원율 측정(→ 04 평가 및 한계)

## 7. 알려진 한계

- 신호 행렬과 라벨식이 모두 **내가 정한 가설**이라, 모델이 그것을 잘 되찾는다는 것은 "파이프라인이 동작한다"는 증거이지 "현실에서 맞는다"는 증거가 아닙니다.
- 단일 시점 스냅샷이라 시계열 변화(추세) 피처는 제한적입니다.
- 일부 카탈로그 자격 조건에 쓰는 사실 27종 중 3종은 스키마에 없어 값 없이 처리됩니다.
