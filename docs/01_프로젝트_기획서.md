# 01. 프로젝트 기획서 — 구독 이탈 예측 & 유형별 맞춤 방지 AI Agent

> LG전자 AX School AI 엔지니어 과정 · Build2 · 6인 팀 · 2026.09.21 ~ 10.13
> 이 문서는 상세 설계 문서들을 읽기 쉽게 정리한 **대표본**입니다. 세부 근거는 각 절 끝의 링크를 봅니다.
> 모든 정형 데이터는 **가설 기반 합성 데이터**이며 실제 LG전자 데이터가 아닙니다. 성능 수치는 "파이프라인이 동작함"을 확인하는 용도로만 해석합니다.

---

## 1. 한 줄 요약

가전 구독·렌탈 고객 중 **30일 안에 해지할 가능성이 높은 고객을 예측**하고, 그 이유를 **10가지 이탈 유형**으로 설명한 뒤, 유형에 맞는 **조치를 AI Agent가 제안**하며, 상담자가 확정·반려한 결과와 고객 설문으로 **새로운 이탈 유형까지 찾아내는** 폐쇄 루프 시스템입니다.

## 2. 문제 정의

| 질문 | 답 |
|---|---|
| 무엇이 문제인가 | 구독 해지는 사후에야 알게 되고, "왜 떠나는지"가 한 덩어리로 뭉개져 대응이 일률적입니다. |
| 누가 쓰는가 | 고객 관리 담당(상담자). 목록에서 위험 고객을 보고 Agent의 조치 제안을 확정하거나 반려합니다. |
| 이탈의 정의 | 기준일 다음날부터 **30일 안에 해지 접수** |
| 풀고 싶은 것 | ① 누가 위험한가(예측) ② 왜 위험한가(유형) ③ 무엇을 해야 하는가(조치) ④ 모르는 이유는 어떻게 찾는가(학습) |

## 3. 접근 방식

예측만 하는 시스템이 아니라 **"예측 → 이유 → 조치 → 학습"** 이 이어지도록 4단계로 나눴습니다.

| 단계 | 내용 | 핵심 기법 |
|---|---|---|
| ① 데이터 생성 | 가설 기반 합성 데이터 30,000 구독, PostgreSQL 약 20개 테이블 | 유형별 신호 행렬 + 라벨 생성식 |
| ② 배치 예측 | 이탈 확률, 위험 등급, 이탈 유형 1~3개 | XGBoost, 보정(Platt), TreeSHAP 유형 도출 |
| ③ Agent | 유형별 솔루션 선택과 고객 메시지 작성 | Rule Engine → LLM → 검증기 → 템플릿 폴백 → 사람 확인 |
| ④ 피드백 루프 | 설문 → 응답 → 신규 유형 후보 발굴 | 후보 Agent + 3회 합의 + 관리자 승인 |

설계 원칙 여섯 가지(요약):

1. **LLM을 믿지 않고 확인한다** — 선택지는 규칙이 정하고, LLM은 그 안에서 고르고 쓰기만 하며, 모든 출력은 검증기를 통과해야 합니다.
2. **정답은 분리한다** — 합성 데이터의 정답(라벨·진짜 유형)은 별도 테이블에 두고 학습·추론에 넣지 않습니다.
3. **사람이 마지막에 결정한다** — 실제 발송 없이 상담자 확정 이력만 `action_log`에 남깁니다.
4. **LLM이 없어도 돈다** — 키 없음·타임아웃·검증 실패 시 템플릿으로 내려갑니다.
5. **새 유형은 한 사람이 정하지 않는다** — 최소 지지 수, 반복 합의, 관리자 승인, 비활성 시작.
6. **한계를 숨기지 않는다** — 합성 데이터 위의 검증은 순환적임을 명시합니다.

## 4. 이탈 유형 10가지

고객 리뷰 약 370건(분류 259건)과 한국소비자원 「가전 구독·렌탈 실태조사」(2025.12) 등을 근거로 팀이 2026-10-07에 확정했습니다. 괄호는 분류된 리뷰 수입니다.

| ID | 유형 | ID | 유형 |
|---|---|---|---|
| T01 | 구독료 부담 (29) | T06 | 방문 일정 불편 (38) |
| T02 | 해지·이사 장벽 (5) | T07 | 매니저 품질 불만 (53) |
| T03 | 재계약·갈아타기 갈등 (6) | T08 | 영업 압박 (7) |
| T04 | 사용 빈도 저하·방치 (3) | T09 | 제품 고장·성능 불만 (22) |
| T05 | 케어 부실·피해 (81) | T10 | AS·고객센터 불만 (15) |

대상 제품군은 의류관리기·건조기·냉장고·세탁기·에어컨·정수기 6종입니다. T02·T04·T08처럼 리뷰 근거가 적은 유형은 "근거가 약하다"고 문서에 그대로 표시했습니다.

상세: `churn_types_10.md`

## 5. 시스템 흐름

```
[합성 데이터 DB] → build_features → XGBoost → 확률·등급
                                      └→ TreeSHAP → 유형 1~3개
        ↓
[Agent]  입력 조립 → Rule Engine(후보 화이트리스트) → LLM(선택·문구)
         → 검증기(실패 시 1회 재시도) → 템플릿 폴백 → 상담자 확정/반려 → action_log
        ↓
[피드백] 설문 5종 → 응답 시뮬레이터 → 후보 Agent → ai_proposal → 관리자 승인
         → 새 유형(T11+)·솔루션을 '비활성'으로 등록
```

상세: `overall_pipeline.md`

## 7. 주요 설계 판단

| 판단 | 이유 |
|---|---|
| 스코어링 단위를 고객이 아닌 **구독**으로 | 고객 1명이 여러 구독을 가질 수 있어 스키마는 1:N을 허용, MVP는 1:1 |
| 피처를 테이블에 저장하지 않고 `build_features(as_of)`로 계산 | 합성 데이터를 자주 재생성하므로 중복 저장이 오히려 불일치 원인 |
| DB 외래키 제약을 두지 않고 **적재 후 무결성 SQL**로 검증 | 재생성·수정이 잦아 적재 순서 제약이 부담. 논리 관계 29개를 검사 쿼리로 확인 |
| 유형 도출을 별도 분류기가 아닌 **SHAP 그룹 합산**으로 | 예측과 설명이 같은 모델에서 나와 일관됨 |
| LLM에게 **자유 생성이 아닌 후보 중 선택**을 시킴 | 존재하지 않는 혜택·과도한 약속을 구조적으로 차단 |
| 새 유형을 **비활성으로** 등록 | 한 번의 자동 발견이 곧바로 고객 조치로 이어지지 않게 |

## 8. 결과 요약 (합성 데이터 기준)

- 시험셋 PR-AUC 0.545 (무작위 0.083), ROC-AUC 0.908, 상위 10% Recall 0.647
- 유형 복원: 1개 이상 맞춤 97.3%, 주 유형 포함 93.8%, 정상 고객 → '유형 없음' 98.6%
- LLM 문구(nano, 프롬프트 v3.4): 1차 통과 84%, 사용 가능 95.5%, 전체 템플릿 폴백 0%
- 자동 테스트 491건 통과
