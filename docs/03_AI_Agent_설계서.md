# 03. AI Agent 설계서 (대표본)

> 정본: `agent_design.md`(입출력·Rule Engine) · `agent_validator_design.md`(검증기·폴백) · `agent_prompt_design.md` · `solution_catalog_design.md` · `survey_simulator_design.md`
> 이 문서는 구조와 설계 판단을 요약합니다. 규칙 전체 표와 프롬프트 전문은 정본을 봅니다.

---

## 1. 목표와 핵심 아이디어

"유형에 맞는 조치를 제안하는 Agent"를 만들되, **LLM이 틀려도 고객에게 잘못된 말이 나가지 않는** 구조를 만드는 것이 목표였습니다.

> **LLM을 믿는 구조가 아니라 확인하는 구조.**
> 규칙이 선택지를 정하고(Rule Engine), LLM은 그 안에서 고르고 쓰며, 검증기가 확인하고, 실패하면 템플릿으로 내려가고, 최종 결정은 사람이 합니다.

## 2. 전체 흐름

```
① 입력 조립 → ② Rule Engine → ③ LLM → ④ 검증기(실패 시 1회 재시도) → ⑤ 템플릿 폴백 → ⑥ 상담자 확정/반려 → action_log
```

| 단계 | 책임 | 비결정성 |
|---|---|---|
| ① 입력 조립 | 예측·유형·구독·이력에서 `AgentInput` 구성 | 없음 |
| ② Rule Engine | 후보 솔루션 화이트리스트 산출 | **없음(결정적)** |
| ③ LLM | 후보 중 선택, 선택 이유, 고객 메시지 작성 | 있음 |
| ④ 검증기 | 규칙 위반 탐지, 1회 재시도 | 없음 |
| ⑤ 폴백 | 템플릿으로 교체 | 없음 |
| ⑥ 사람 | 확정/반려 | - |

## 3. 호출 경로(mode)

| mode | 조건 | LLM |
|---|---|---|
| `ACTION` | HIGH/MID + 유형 1~3개 | 호출 |
| `NO_TYPE` | HIGH/MID + 유형 없음 → 만족도 조사 제안 | 호출(설문 안내 문구) |
| `SURVEY_ONLY` | LOW 중 위험 순위 20~30% | 호출 안 함(템플릿) |
| `NONE` | 그 밖의 LOW | 호출 안 함 |
| 대체 | ACTION인데 자격 있는 후보 0건 → 만족도 조사로 대체 | 호출 |

위험이 낮거나 유형이 없을 때까지 LLM을 부르지 않아 **비용과 오작동 면적을 줄였습니다.**

## 4. Rule Engine — 결정적으로 후보를 만든다

### 4.1 판정 순서 (v3)

1. 경로(mode) 결정
2. 후보 생성: 채택된 유형의 활성 솔루션
3. 광고 동의 확인 → 자격 조건(`eligibility`) → 쿨다운 순으로 제외
4. 그리디 선택(정렬 키 `-기여도 비중, 유형 순위, priority, offer_cost, solution_id`)

### 4.2 제약

| 제약 | 값 |
|---|---|
| 쿨다운 | 같은 솔루션 14일(확정된 조치만) |
| 구분 중복 | 같은 구분(정보제공·담당자조치·혜택제안·제품조치) 1개 |
| 동시 조치 | 최대 2개 |
| 비용 상한 | `offer_cost > 0`인 솔루션만: 1회 ≤ 월 요금×1.0, 최근 90일 누적 ≤ 월 요금×2.0 |
| 광고 동의 | 값이 없으면 **미동의**로 간주 |
| 필수 자격 조건 | "프로모션 종료", "예정 방문" 같은 사건 조건은 값이 없으면 후보 제외 |

### 4.3 시뮬레이션이 바꾼 설계

초안(v1)은 단계를 하나씩 순서대로 걸렀습니다. 상위 6,000건 시뮬레이션에서 **두 번째 유형이 후보를 못 받는 비율이 60%** 로 나와 구조를 바꿨습니다(v2): 선택을 두 라운드로 나눠 "유형별 대표 1개"를 먼저 뽑고 남은 슬롯을 채우도록 해서 최종 **6.7%** 까지 줄었습니다. 또 무료여야 할 A/S·교환이 비용 상한에 막히던 문제는 `offer_cost`에 넣지 않는 것으로 풀었습니다.

| 지표(10유형·확정 카탈로그, 상위 20% 6,000건) | 결과 |
|---|---|
| 제안 조치 0개 | 0.2% |
| 주 유형 미커버 | 0.2% |
| 두 번째 유형 미커버 | 6.7% |
| 유형 평균 커버율 | 90.9% |

시뮬레이션은 시드 1~3에서도 비슷한 범위였고, 광고 동의율·쿨다운·동시 조치 수의 민감도도 확인했습니다. (동시 조치 1개면 두 번째 유형 미커버가 99.9%로 급증해 2개를 유지.)

발견한 한계도 기록했습니다: 비용이 있는 활성 솔루션이 사실상 2건뿐이라 비용 상한은 **안전장치 역할**에 그치고, 정렬 키의 마지막 `solution_id`가 편중을 만들 수 있어 `priority` 컬럼을 추가했습니다.

## 5. LLM 단계

- OpenAI Structured Outputs로 JSON 스키마를 강제하고, `solution_id`는 후보 목록으로 제한(enum)
- 선택지는 후보 안에서만. 액션 문구에는 nano, 신규 유형 후보 생성에는 mini 사용 (모델명은 설정값으로 관리)
- 프롬프트에 **고객 이름·구독 ID·내부 분석값을 넣지 않음**. 고객에게 보여도 되는 값만 `message_facts`로 전달
- 메시지 형식: 제목 + 첫 문장 + `▶ 라벨: 값` 0~4줄 + 마무리, 400자 이내, 존댓말
- API 키는 환경변수에서만 읽고, 오류 문자열에 섞인 키 조각은 저장 전에 가림 처리

## 6. 검증기 — 확인하는 구조의 핵심

LLM 출력의 모든 필드를 규칙 기반으로 검사합니다(hard: 재시도·폴백 대상, soft: 기록만).

| 범주 | 예 |
|---|---|
| 형식·구조 | JSON 파싱, 스키마, 후보 밖 솔루션, 개수·중복·구분 중복 |
| 숫자 | 선택 이유·메시지의 숫자가 **입력에 있는 값(값+단위)** 인지 대조 |
| 내용 안전 | 내부 식별자·시스템 용어·연락처·링크 유출, 이탈/위험도 등 내부 용어 노출 |
| 표현 | 압박·보장·해지 방해 표현, 후보 문구에 없는 혜택 표현(무료·할인 등) |
| 광고 | 광고성이면 `(광고)` 표기 |
| 구분별 필수 요소 | 예: 요금이 바뀌는 안내에는 총 비용·위약금 언급 |
| 언어 | 한자·일본 문자·키릴 문자·영어 문장, 보이지 않는 문자 |
| 유형 없음 | 불만·이탈 단정 금지, 열린 질문 형태 |

우회 시도(보이지 않는 문자, 전각 문자, 한글 숫자, URL, 영어 문장 등) 30건 이상을 테스트로 고정했고, 방어 코드 15곳을 하나씩 일부러 망가뜨려 **15/15를 테스트가 잡는지** 확인했습니다(뮤테이션 점검).

### 폴백

| outcome | 의미 |
|---|---|
| `pass` / `retry_pass` | 1차 / 재시도 후 통과 |
| `partial_template` | 문구·근거만 실패한 항목만 템플릿으로 |
| `full_template` | 구조 실패나 LLM 오류 시 전체 템플릿 |
| `no_action` | 후보 0건 등 |

화면에는 문구 출처("AI 작성"/"기본 문구")와 재시도 횟수를 표시합니다.

## 7. 사람 확인과 이력

상담자의 확정/반려만 기록하며 실제 발송은 하지 않습니다(시뮬레이션). 확정된 조치만 `action_log`에 쌓여 쿨다운·누적 비용 판정에 쓰입니다. 복합 솔루션(톡+내부 전달)은 두 부분을 따로 확정하며 결정 메모를 남깁니다.

## 8. 피드백 루프 Agent (④)

```
설문 5종 → 응답 시뮬레이터 → 집계 → 후보 Agent(규칙 근거 묶음 → LLM → 검증기 → 3회 합의) → ai_proposal → 관리자 승인 → 새 유형 T11+ (비활성)
```

- 설문 5종: post_action, post_churn, no_type, no_candidate, survey_only
- 응답은 시뮬레이터가 **숨은 주제**(`synth_truth_topic`)로 생성하며, 이 정답은 Agent에 전달하지 않고 평가에만 사용
- 신규 유형 후보 규칙: 최소 지지 수(8), 3회 독립 실행 합의, 관리자 승인, 비활성으로 등록
- 통계적 셀 탐지 방식은 거짓 양성이 약 70%여서 폐기하고 규칙 근거 + LLM 방식으로 전환

## 9. 테스트

## 10. 설계 판단 요약

| 선택 | 대안 | 이유 |
|---|---|---|
| 규칙이 후보 확정, LLM은 선택·작문 | LLM이 솔루션까지 자유 생성 | 존재하지 않는 혜택·과대 약속 차단 |
| 검증 실패 시 템플릿 폴백 | 실패 시 오류 | 상담 현장에서 빈 화면이 가장 나쁨 |
| 확정된 조치만 쿨다운 반영 | 제안 즉시 반영 | 제안만 하고 반려된 것을 쿨다운으로 막으면 안 됨 |
| 값 없는 필수 조건은 후보 제외 | 값 없으면 통과 | 확인되지 않은 일을 고객에게 단정하지 않기 위해 |
| 새 유형은 비활성으로 시작 | 즉시 활성 | 자동 발견의 오류 영향 격리 |
